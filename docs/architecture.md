## 2. Architectural Principles

The design of PBIP Lens is governed by two key low-coupling principles:

### A. Hexagonal Architecture (Ports & Adapters)
All business and parsing logic resides purely within `src/core/`. This directory is strictly prohibited from importing Node.js modules (`fs`, `path`) or VS Code modules (`vscode`).
* **Ports**: Defined in `src/core/ports/` (e.g. `IFileSystem`, `ILogger`).
* **Adapters**: Defined in `src/infrastructure/adapters/` (e.g. `NodeFileSystem`, `VSCodeLogger`) and implement these contracts.
* **Wiring**: Coupling is resolved by injecting implementations when initializing engines in the entry point of the infrastructure (`ExtensionController`).

### B. Strategy Pattern in Audits (Linter)
The logic to validate model health is not hardcoded within the analysis engine.
* **Abstract Rules**: Each rule implements the `IAuditRule` interface.
* **Injection**: The `AuditEngine` receives a dynamic array of `IAuditRule[]`. When `analyze()` is executed, it recursively evaluates each injected rule on the graph without knowing its internal logic, collecting a structured list of violations (`RuleViolation`).

## 3. Initialization and Signatures of Core Classes (`src/core/`)

Core semantic engine, mutation, and audit classes are instantiated and injected within the global controller:

### `PbipProjectReader`
* **Purpose**: Reads the `.pbip` file and extracts paths and references to the model folders.
* **Signature:**
  ```typescript
  constructor(private fs: IFileSystem)
  ```

### `TmdlNodeExtractor`
* **Purpose**: Parses TMDL files in a lightweight manner using heuristic indentation to extract measures and columns.
* **Signature:** (Empty implicit constructor).

### `ReportParser`
* **Purpose**: Parses visual files in the `.Report/` folder (modern PBIR format or legacy `report.json`).
* **Signature:**
  ```typescript
  constructor(private fs: IFileSystem)
  ```

### `SecurityParser`
* **Purpose**: Parses security roles and static filters (RLS).
* **Signature:**
  ```typescript
  constructor(private fs: IFileSystem)
  ```

### `RelationshipParser`
* **Purpose**: Parses relationship definitions from TMDL files and registers them in the semantic graph.
* **Signature:**
  ```typescript
  constructor(private fs: IFileSystem)
  ```

### `ResolutionBinder`
* **Purpose**: Resolves pending dependencies and binds edges in the graph transactionally.
* **Signature:**
  ```typescript
  constructor(private graph: SemanticGraph, private registry: PendingReferenceRegistry)
  ```

### `SemanticEngine`
* **Purpose**: Main orchestrator of the entire static analysis pipeline of the model.
* **Signature:**
  ```typescript
  constructor(
      private projectReader: PbipProjectReader,
      private nodeExtractor: TmdlNodeExtractor,
      private lexer: DaxLexer,
      private parser: StructuralParser,
      private graph: SemanticGraph,
      private registry: PendingReferenceRegistry,
      private binder: ResolutionBinder,
      private reportParser: ReportParser,
      private securityParser: SecurityParser,
      private logger: ILogger
  )
  ```

### `PurgeEngine`
* **Purpose**: Allows physical mutations on disk by safely deleting orphan measures from their TMDL declarations.
* **Signature:**
  ```typescript
  constructor(private fs: IFileSystem, private logger: ILogger)
  ```

### `AuditEngine`
* **Purpose**: Extensible linter that runs strategy-based rules looking for anomalies in the graph.
* **Signature:**
  ```typescript
  constructor(private rules: IAuditRule[], private logger: ILogger)
  ```

### `GraphQueries`
* **Purpose**: Exposes lightweight queries on the semantic graph to be displayed in Webviews and TreeViews.
* **Signature:**
  ```typescript
  constructor(private graph: SemanticGraph, private auditEngine: AuditEngine)
  ```

### `EngineFactory`
* **Purpose**: Static factory responsible for instantiating `SemanticEngine` by internally resolving and wiring all its domain dependencies.
* **Signature:**
  ```typescript
  public static createSemanticEngine(fs: IFileSystem, logger: ILogger): SemanticEngine
  ```

## 4. Extension Entry Point

The main entry point where the extension starts upon activation in VS Code is the file **`src/extension.ts`**.

* **`activate(context)` function**: VS Code native lifecycle function triggered when the extension is activated. It initializes an instance of `ExtensionController` (defined in `src/extension/ExtensionController.ts`) and registers global editor commands.
